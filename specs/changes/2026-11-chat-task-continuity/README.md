# 从原聊天接续受托工作

Status: verified

范围：Super Bot 单仓库，REQ-006、007、008。创建于 2026-11-27。

## 用户体验和验收

1. 用户交代调研，旧 Worker 轮次先结束、名下后台 Job 后退出。Bot 保留明确的等待和冲突占用，收到同一 Job 终态、结果已消费且原会话确已安静后，沿用原任务、材料和授权继续一次。聊天回报工作结果。发生暂停、接管或关闭时服从最新指示。
2. 等指定条件时，用户说「报告里再写一条，其他照旧」，原观察继续，下一轮同时收到已授权步骤和补充。「改为只查」「暂停」「撤回下一步」则让旧成功事件失效。无关任务不受影响。
3. 用户已经授权一个具体动作。旧阶段的 MR 操作已经结束，Bot 自行核实前置以及当前目标动作的状态。确知未启动时走正式入口一次；已启动则跟踪原作业；回执未知则只读追踪那个目标。原聊天能看到真实回执或唯一缺口。没有真实授权或需第三方独立审批时，在聊天说明具体对象、谁能处理，Bot 继续跟踪。
4. 用户能在原聊天补充、回答、核对、授权继续、暂停、关闭、要求返工或明确接受当前成果。面板作为相同命令的第二个入口。Bot 根据已验证的状态主动执行可代办步骤；需要本人作决定时，在原聊天问一次并接收自然语言回答。用户无需复制 ID、复述已有授权或打开面板勾选。区分旧轮中断、当前等待、Worker 已开跑、正式结果。
5. 绑定本人在飞书群中发送的文字真正进入 Bot 会话后，在原消息加一个固定收到表情。排队、接收事件、Worker 状态均不替代入站送达回执。重复事件最多一次尝试；表情失败不影响收信或回复。

## 实现边界

- 复用现有 SQLite、阶段、指示、原生事件、管理工具和收件箱。内部变化按事件核实，只在状态实质变化时通知。外部条件低频、有期限检查，配置或权限恢复后可重查，重启延用已过时间。用户主动询问随时读最新事实。
- 旧轮结束和稍后后台安静各留一份事实。宿主记录旧轮当时确切的 Job 身份及未满足条件；收敛时再核对原任务、绑定、轮次结束、后台树、未消费消息、审批和占用。只在这些证据能够归属原轮时自动恢复。沿用已完成工作的检查点；旧轮不会因为后来安静而补交成果。找不到证据时，Bot 先查宿主，再报告当前缺什么。
- 追加或替换由 Manager 根据已验证的用户原话决定，账本事务落实。把追加指示随已存在的阶段派发一起消费，保留消息身份与限制。变更计划让旧派发和迟到观察同时作废。
- 可验证的外部动作先支持现有 GitLab 业务流中的一个明确目标。使用项目、实例、确切流水线和手动作业身份。正式入口沿用被授权的 Worker 身份，保持提供方权限与审批；只读观察凭据只作查询。受信 GitLab 读取可来自当前配置，也可通过已经登录同一实例的本机 glab 的固定 API 调用。Manager 与 Worker 不提供任意命令或网络地址给观察器。重复提交、重启和网络结果不明时按同一对象查询。其他工具继续按实际回执执行，不以模型复述代替核验。隔离验收使用可计数的合成正式入口。
- 经确认的任务内人工动作复用面板的应用命令。用户的接受、人工确认来自原生 owner 消息或有效的本人飞书绑定。任务归属、当前版本和原生权限与面板一致。新自动流程不依赖人工确认。开发者配置和第三方身份认证不是业务恢复流程的一步。
- 飞书表情挂在原消息首次进入本机原生会话的已提交回执上，使用现有 SDK 与绑定信息。省略独立队列、额外模型回复及失败循环。

## 范围和验证

各需求可独立验证。优先修复原等待与追加冲突、晚到 Job 结果，再接上外部动作。采用现有 worker/manager、资源与版本约束。产品不引入通用工作流引擎、任意工具授权开关或第二套聊天入口。测试使用隔离账本、真实 DSH 宿主和模拟远端，部署验证在本机 3080。需求与上一轮复审保存在 workspace 的 requirements 目录。

## 一轮独立评审后的修订

**晚到回执。** 为旧轮保留当时的 quiet=0。单独核对持久化原生事实：原轮中断或失败 → 属于该轮的 Job 全部进入终态 → 原生系统投递这些 Job 的结果 → 消费通知的原生轮次结束。消费轮只能含这些可识别通知，不能夹入真人输入、额外工具或未知来源。关联失败、未消费、仍有子会话或审批都保留具体原因。重启后读回，多个终态只产生一次后继。人工暂停、关闭、接管优先；系统为故障挂起和用户主动暂停须可区分。下一步有外部效果时独立核对其目标。未知工具产生的潜在冲突仍须核对。

**首次执行和读回。** 从原任务中的可信 MR 引用和已有用户授权发现同实例、项目的目标 pipeline 和 manual job；多个候选且授权无法区分时，通过原聊天问一次业务名称。使用 Worker 的正式执行入口和现有权限。提交前在事务内认领确切的实例、项目、pipeline 和 job ID，只允许一个执行者。提交可能发出后，回执丢失，或 GET 暂时仍是 manual，均只在期限内读回原对象；不能自动重新 POST 或换一个重试生成的 job。可证实的异目标旧写入不妨碍已授权新动作，仍可能改到同一目标的旧写入须先核对。以隔离远端收到的请求次数验收。只读观察恢复后在原任务接回；访问凭据只发往它配置的可信来源。持续 pending 也受同一持久期限约束，到期在原聊天给一次实际缺口和可答复的问题。

| 用户在原聊天的表达 | 与面板共用的业务动作和约束 |
|---|---|
| 追加、更改目标、答复、撤回、返工、继续 | 复用 task.revise、respond、rework、dispatch 等既有命令和版本校验。用户说只读、暂停或撤回时，使冲突的旧计划失效。 |
| 先停、停当前执行、继续、核对后先别跑、核对后接着做、关掉 | pause/resume/stop/close、run.recover、run.recover-and-continue；自动可核对项由 Bot 自行核对。仅在有具体未确认效果时向本人核实事实，普通「继续」不证明旧写入已结算。 |
| 我接受刚才这个成果 | result.accept，校验当前结果版本，保存实际发话的本人来源；自动提醒、Worker 文本不能代签。 |
| 改目标、接回/关联/解除原 Worker、核对会话 | task.revise、session.reconcile/attach/detach；由 Bot 查归属与当前会话，尊重已接管的会话和任务状态。 |
| 重试、标为已处理 | 对当前任务相关的 manager.notification 重试/解决操作保留来源检查。Bot 先用已有只读手段核对事实。 |

同一聊天中存在两个可能的任务或版本，Bot 用用户能识别的名称/成果问一次。答复只作用于刚才列出的目标；过期或来自其他聊天时重新查证。宿主真正需要用户本人身份的原生审批/登录依其提供方约定执行。面板的导航、展开、复制等展示控件无须建独立命令；能读的内容在原聊天可查。

接口依据：[GitLab Jobs API](https://docs.gitlab.com/api/jobs/)、[glab api](https://docs.gitlab.com/cli/api/)、[飞书消息表情接口](https://open.feishu.cn/document/server-docs/im-v1/message-reaction/create)。
