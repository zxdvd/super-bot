浏览器回归使用确定性模型和合成飞书传输。以下租户联调保留真实 DSH 宿主、官方 SDK 长连接和飞书群，模型仅回显本轮验收标记。飞书端用已登录的 lark-cli 以用户身份发言、读取群消息，宿主端核对原生 Manager 会话收据。

- 新建私有群后确认群主为授权账号，初始成员为该账号及机器人。首次联调发现飞书建群成功后，机器人的已加入群列表可能稍晚才返回该群。修复后，第二个应用在一次建群请求内完成绑定。权限和延迟复查均有定向回归。
- 在未运行本机 CLI 事件监听的应用上，预览并绑定一个已有测试群。网页输入和助手回复在群中各出现一次。连续三条不同的真人 `@` 消息在 SDK 分发和同一 Manager 中均各出现一次，群中也收到三条对应回复。
- 绑定前在 Manager 中生成一段对话。首次绑定后群内没有这段历史。解绑期间在群中发送新的 `@` 消息，重绑后 Manager 中该输入和回复计数均为零，已有输入的事件 ID 及回复数保持不变。
- 另两组使用其他网关也配置过的应用。两个测试宿主各收到了 1/2 和 2/3 条独立用户消息。未到达的消息在对应宿主中没有收据，无法据此断定实际投到了哪个接收端。部署时每个 App ID 应有唯一的事件接收服务。飞书会将同一应用的长连接客户端作为一组分发事件。[官方 SDK 的集群模式说明](https://github.com/larksuite/node-sdk/blob/main/README.zh.md)
