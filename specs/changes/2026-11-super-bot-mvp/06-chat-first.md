# 06 聊天主流程

本页记录 2026-11-07 用户确认的产品修正：与 Bot 聊天，由它自己安排执行并回来交付。它优先于旧方案中“先进入 Dashboard 操作任务”的体验描述；底层权限、证据和恢复契约不变。以下均为待实现目标，不是当前安装包能力声明。

## 首个可演示流程

1. 用户从 Super Bot 选择一个 Bot，直接进入它的当前对话。首次创建只需名称，职责可选；未填写时使用明确的通用助手默认职责。参考资料放设置中。创建后直接准备并打开对话，不再让用户单独“启用管理”。模型选择/账号配置作为一次性引导，未配置不自动执行。
2. 用户说：“帮我写一份给新同事看的项目介绍，先写到你自己的工作目录里。”Bot 询问必要的项目背景或使用用户已经给出的资料。用户不必说“创建任务”，也不必填写目标、范围、验收字段。
3. Bot 简短说明准备交付什么，在当前授权范围内建立任务并安排 Worker，然后告诉用户已安排。简单目标只建一项任务，不为展示规划能力机械拆分。日常问答直接回答，不建任务。
4. Worker 在后台执行。Bot 通过已有重要事件得到问题、失败或成果；普通进度不持续唤醒模型。用户可以继续聊天、询问进展或离开页面，不必轮询执行会话。
5. 成果可检查后，Bot 在同一对话回来交付：做了什么、成果入口、检查了什么、还有什么未验证，以及是否需要用户确认。默认说“已提交，待你确认”；任务只有经既有验收规则才完成。
6. 用户说“再精简一些”，Bot 针对明确的那份成果发起返工；Worker 追问时，用户也在 Bot 对话中回答。最终接受通过用户明确点击的确定性操作完成。

聊天中能打开关联任务或执行会话以查看细节，但日常交代、追问和收到成果不需要在多个页面间搬运信息。

## 入口的最小实现

- 复用 DSH 原生聊天。先核实是否有适合直接复用的组件；有则使用，没有则选择 Bot 后直接打开已绑定的原生对话，并保留可发现的“工作”入口。两者都必须满足默认进入聊天，不增加中间工作台操作。
- 不自建输入框、流式消息协议、聊天历史数据库或模型设置页。任务页面不再是默认首页；“新任务”表单作为可选高级操作保留。
- 用户看到 Bot 名称和自然语言状态。Manager、Run、代数、rowVersion 等实现概念留在诊断/详情中，不作为主流程操作要求。
- 模型不可用时有明确配置入口；工作面板仍可查询、停止和处理恢复。页面关闭不等于停止后台宿主。

## 复用与最小补齐

| 已有部分 | 本轮处理 |
| --- | --- |
| Bot 身份、配置快照、Manager 绑定和原生会话 | 复用；改变默认导航、首次创建和对话说明 |
| Task/Run/Input/Result/Attention 与 SQLite 事务 | 复用；不再让用户手工完成正常派发步骤 |
| Manager 的 list/detail/create/dispatch/review | 复用；补自然请求澄清、简短接单和面向用户的交付行为 |
| Outbox 重要事件与自动唤醒 | 复用；确保问题、失败和成果确实出现在当前 Bot 对话，不能只写 Review 或面板状态 |
| 回答、返工、人工接受的应用命令 | 复用；补受限的对话入口和确定性确认入口，不另写业务规则 |
| Dashboard、审批、停止与恢复 | 保留为辅助工作视图及异常出口，不扩展新的管理平台 |

已核对当前代码：Manager 工具尚无对话回答/人工返工入口；自动唤醒已存在，但“原对话可读交付”没有独立验收；主 UI 仍需点击启用/打开管理对话。因此本轮不把“已有 Manager”当成聊天体验已经完成。

## 对话与任务的最小约束

- 明确区分普通问答、待澄清的工作意图、已安排的工作。缺少执行所必需的资料时先在对话澄清；程序不能因一条闲聊自动创建任务。允许 Bot 根据请求归纳范围和验收条件，但不得自行扩大目录或工具授权。
- 对话创建任务关联实际用户请求来源，复用原生消息 ID 和现有记录机制；同一次工具调用重复到达仍只生效一次。不同消息是否是追加或新任务由 Bot 结合上下文判断，有歧义先问，不做跨消息全文去重平台。
- 新 Worker 继续使用独立会话和专用目录，并沿用已明确选择的模型。原生执行会话只供按需查看/接管，不要求用户手动准备或逐次点击开始。
- 对话回答/人工返工只针对有效、属于当前 Bot 的问题或成果，校验当前版本；请求来源必须由宿主上下文确定，不能相信模型自填“用户已同意”。Worker 报告和自动唤醒不能冒充用户回答。多项工作同时等待时，Bot 指明对象或先澄清，不能默认操作最近一条。
- 人工验收保留真实用户确认。优先复用宿主可用的确定性按钮；若聊天内按钮不支持，交付消息提供直达该成果确认位置的入口，不让用户重新搜索任务。自然语言“可以了”可以引导确认，不能由模型写 humanAcceptedAt。
- 问题、失败、成果等重要变化沿用已有事件身份、串行管理与预算。重复事件不再次执行工作；通知投递不明仍转核对，不为追求聊天流畅而盲重发或另跑一遍。
- Manager 替换后使用当前有效对话继续交付；旧对话不恢复权限。成果链接必须指向当前有效对象，不能把本机路径当作用户一定能打开的链接；交付入口的可用性需要真实 UI 验证。

## 演示边界

第一轮只要求一项本地文档工作贯穿聊天到交付，再扩展一次回答和一次返工。用户提出 Shell、跨应用等当前不支持的任务时，明确说明限制和可做的部分，不假装已经执行。

不增加通用任务 DAG、自动记忆、消息总线、外部 IM、第二执行后端或全新的聊天壳。既有 65 项测试与 11 项宿主契约作为回归基线；只为新增入口、权限和投递行为补必要测试。聊天流程的真实模型表现单独验证，不能拿确定性模型的成功替代产品验收。
